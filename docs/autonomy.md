# Автономное создание и ведение рекламы

Рабочий интерфейс пользователя — разговор с Codex. Агент готовит JSON и вызывает
команды; вручную составлять API-запросы не нужно. Один проект — один выбранный
кабинет и среда, локальная база и собственные правила. Эта версия поддерживает
поисковые ЕПК с ручными ставками и адаптивными объявлениями.

## Подключение и однократное согласование

1. Создайте проект и пройдите `setup` в своём терминале по README. Для создания
   с нуля кабинет может быть пустым. Ключи не передавайте агенту в чат.
2. Codex выясняет продукт, посадочную, регионы, исключённый спрос, критерий
   квалифицированного лида, бюджет, срок и частоту проверок. Сохраняет бизнес-правила
   в `projects/<id>/business-rules.md`, без персональных данных клиентов.
3. Агент копирует [пример допуска](../examples/direct-grant.example.json) в проект,
   заполняет актуальные project_id/context_hash из `context`, кабинет, валюту,
   срок и конкретные лимиты. `approval_source` ссылается на запись решения владельца.
   Пример содержит просроченные даты и заглушки; это не активированный допуск.
4. `grant-check` проверяет черновик. Codex показывает область действий, бюджет,
   срок, домены, регионы, автоматический запуск после модерации, условия остановки,
   задержку расхода и SHA-256. Владелец согласует именно эти правила.
5. Агент активирует согласованную версию с тем же SHA. После этого обычные операции
   внутри правил выполняет самостоятельно. Увеличение пределов, расширение кабинета,
   изменение доменов/регионов и продление требуют новой версии и согласования.

```sh
.venv/bin/python scripts/directologist.py --project my-project direct grant-check --input projects/my-project/grant.json
.venv/bin/python scripts/directologist.py --project my-project direct grant-activate --input projects/my-project/grant.json --confirmation SHA256
.venv/bin/python scripts/directologist.py --project my-project direct grant-status
```

Все суммы в допуске и операциях — целые микроединицы валюты кабинета:
`300000000` означает 300 RUB для рублёвого кабинета. Это не копейки.

| Поля DirectGrant v2 | Значение |
|---|---|
| project_id, context_hash, version | Точная привязка и новая неизменяемая версия |
| environment, client_login, currency | production либо sandbox; кабинет и валюта |
| starts_at, expires_at | ISO datetime с часовым поясом; период не более 31 суток |
| campaign_ids, allow_create | Существующие ID из setup; разрешение создавать новые |
| allowed_operations | Закрытый список операций из `capabilities.direct_v2` |
| allowed_domains, region_ids | Точные HTTPS-домены без wildcard; положительные ID регионов |
| max_campaigns, max_operations_per_day | Кампании в области допуска; число шагов в сутки UTC |
| max_daily_budget_micros | Сумма дневных параметров всех управляемых кампаний, включая остановленные |
| max_total_budget_micros | Общий предел на период, расход учитывается с НДС |
| max_bid_micros | Максимальная базовая ставка ключа/автотаргетинга |
| spend_buffer_micros | Резерв до общего предела для задержки статистики и остановки |
| trust_mode, accept_delayed_spend | `trusted-local`, явное принятие задержки отчётов |
| approval_source | Запись конкретного согласования, не выдуманное разрешение |

В область входят выбранные существующие кампании и созданные этим проектом в той
же среде, если `allow_create: true`. При продлении учитываются ранее созданные
кампании. Снятие allow_create убирает их автоматическое включение: сначала остановите
их или явно выберите в setup и новом допуске. Не оставляйте кампании без наблюдения.

Перед записью скрипт читает расход и дополнительно резервирует дневные параметры
кампаний на оставшиеся дни, минимум на семь дней для каждой. Это консервативная
проверка, она может отклонить действие раньше фактического исчерпания бюджета.
Дневной параметр API не обещает равномерный расход по дням: ручные бюджеты платформы
могут исполняться как недельные. Максимальная базовая ставка не равна предельному
CPC с внешними корректировками. Дата EndDate ограничивает срок показов на стороне
Директа; в API она заканчивается в 00:00 по Москве. Агент задаёт её не позже
истечения допуска. Полного мгновенного hard cap у этой локальной системы нет.

## Создание кампании

Агент проверяет продукт и спрос, готовит [blueprint](../examples/campaign.example.json),
сохраняет его в проект и запускает:

```sh
.venv/bin/python scripts/directologist.py --project my-project direct build --input projects/my-project/campaign.json
```

До первого write проверяется весь состав. counter_ids может содержать только
счётчик, выбранный в подключении Метрики; без него используйте пустой список. Затем по одному журналируемому шагу:
создание пустой кампании → остановка → группы → настройки уже созданного платформой
автотаргетинга и его ручная ставка → ключи → адаптивные объявления → модерация.
Принятые объявления запускаются, если `auto_start: true` и `campaign.resume`
разрешён владельцем. Непринятые дают WAIT_MODERATION или MODERATION_REJECTED.

При WAIT_MODERATION повторяется **тот же** blueprint с тем же request_id.
Подтверждённые шаги не отправляются заново. При MODERATION_REJECTED агент читает
актуальные объявления, исправляет тексты отдельными `ad.update`/`ad.moderate`
операциями и сохраняет связь с исходной сборкой. Отдельные creative-компоненты
могут требовать проверки в кабинете. Изменять blueprint с уже использованным ID нельзя.
При ручном изменении состояния завершённой кампании повтор сборки возвращает
STATE_CHANGED, не возобновляет показы повторно.

## Цикл ведения

При каждом пробуждении агент восстанавливает `context`, читает бизнес-правила и:

1. Вызывает `direct cycle`. Он проверяет расход, срок и активные кампании,
   выполняет защитную остановку при нарушениях и возвращает статусы модерации.
   STOP_UNCONFIRMED требует уведомить владельца и проверить кабинет.
2. Продолжает ожидающую модерацию сборку; собирает актуальную статистику.
   `collect`/`analyze` дают проверенное evidence по конкретной цели.
   `direct performance` и `queries` — детали по условиям показа и запросам.
3. Codex оценивает достаточность выборки, задержку конверсий, коммерческий интент,
   реальные лиды/продажи и альтернативу наблюдения. Числа считает Python.
4. Обоснованное изменение оформляет точной операцией. `prepare` читает актуальный
   before и формирует план; `apply` ещё раз сверяет данные и действующий допуск.
5. После VERIFIED сохраняет результат и окно следующей оценки. Уроки вводит через
   согласованную learning-policy, спорные — владельцу. Нельзя учиться на выдуманных
   результатах или менять права с помощью урока.

```sh
.venv/bin/python scripts/directologist.py --project my-project direct cycle
.venv/bin/python scripts/directologist.py --project my-project direct queries --date-from 2026-09-01 --date-to 2026-09-07 --output projects/my-project/queries-2026-09-07.json
.venv/bin/python scripts/directologist.py --project my-project direct performance --date-from 2026-09-01 --date-to 2026-09-07
.venv/bin/python scripts/directologist.py --project my-project direct prepare --input projects/my-project/operation.json --output projects/my-project/plan-001.json
.venv/bin/python scripts/directologist.py --project my-project direct apply --input projects/my-project/plan-001.json
```

Замените примерные даты фактическим периодом до 31 дня. С `--goal ID` детальные отчёты включают конверсии выбранной цели с моделью AUTO;
дробные значения сохраняются точно, неизвестные — null. Они не содержат
квалифицированных лидов: для них нужны CRM и настроенная атрибуция. Query — фактический
запрос, Criterion — условие показа; это разные поля. Отчёт запросов может не включать
весь трафик. `--` вместо CriterionId не является ID объекта для изменения.
`--output` создаёт новый файл и не перезаписывает существующий.

Внешний `status: OK` в ответе CLI означает, что команда обработана. Смотрите
`result.status`: только VERIFIED подтверждает конкретный write. UNKNOWN/PARTIAL
останавливают следующие обычные записи до сверки, а не разрешают новый request_id.
Команда `propose` сохраняет обоснование и сама рекламу не изменяет.

## Операции

[Пример операции](../examples/operation.example.json): request_id, action, object_id,
params. У создания object_id = null; остальные операции используют точный числовой ID.

| action | params |
|---|---|
| campaign.create | name, start_date, end_date, daily_budget_micros, counter_ids, negative_keywords |
| group.create | campaign_id, name, region_ids, negative_keywords |
| ad.create / ad.update | titles (1–7), texts (1–3), href; для создания ещё group_id |
| keyword.create | group_id, text, bid_micros |
| keyword.update | text; API может вернуть новый ID — использовать возвращённый |
| keyword.bid | bid_micros |
| keyword.autotarget | categories и brands, как в blueprint |
| campaign.budget | daily_budget_micros |
| campaign.negatives / group.negatives | negative_keywords: полный итоговый список, сохранить прежние исключения |
| campaign.pause/resume, ad.pause/resume/moderate, keyword.pause/resume | Пустой объект `{}` |

Добавление и изменение объявлений выполняются при остановленной кампании. Для
возобновления нужен принятый креатив, разрешённые посадочные и регионы, ручная
поисковая стратегия и проверенные ставки. РСЯ и автоматические стратегии требуют
другого адаптера, их нельзя подменять произвольным API payload.

## Работа по расписанию

После согласования частоты попросите Codex выполнять ведение по расписанию в той
же задаче и локальном каталоге. Файл проекта хранит бизнес-правила и пути активных
blueprints; промпт расписания читает их при каждом запуске, не копирует секреты.
Используйте механизм расписаний приложения (для продолжения задачи — heartbeat),
если он доступен. Не создавайте отдельный worktree: `projects/` исключён из Git,
ему нужны та же база и хранилище ключей. До расписания проверьте один цикл вручную.

Пример задания, в котором Codex подставляет фактический project_id и каталог:

> Используй directologist для проекта my-project в согласованном локальном каталоге.
> На каждом запуске восстанови context и бизнес-правила, выполни direct cycle,
> продолжи ожидающую модерацию сборку, проверь свежие отчёты и примени обоснованные
> изменения внутри действующего DirectGrant. UNKNOWN/PARTIAL сначала сверяй.
> Не продлевай допуск и не повышай лимиты самостоятельно. Сообщай о выполненных
> изменениях, существенных результатах, сбоях и необходимых решениях; при отсутствии
> новых событий не отправляй уведомление. По окончании допуска останови кампании,
> проверь остановку и приостанови расписание; при неподтверждённой остановке уведомляй
> владельца и продолжай только защитную проверку.

Для локальных файлов компьютер должен быть включён, приложение запущено,
сеть и доступ к хранилищу ключей разрешены настройками среды. Расписание создаётся
у конкретного пользователя; установка репозитория сама его не включает.
[Официальная документация расписаний](https://learn.chatgpt.com/docs/automations?surface=app).

## Проверка и источники

`demo_autonomy.py` воспроизводит создание → модерацию → запуск → повтор без дублей,
потерянный ответ, сверку и бюджетную остановку на подменённом API с запретом сети.
Это проверка программного процесса, не реальная API-приёмка. Перед первым рабочим
расходом пользователя проверяется доступ и фактическая совместимость его кабинета;
sandbox может быть отдельным этапом проверки, но не заменяет production-допуск.
