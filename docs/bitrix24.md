# Битрикс24 для директора

Подключён 12 ноября 2026 к `https://sovetov-as.bitrix24.ru` через существующий входящий webhook в macOS Keychain. Новый клиент — `scripts/bitrix24.py`. Он не использует прежний Bridge, crm-local, допуски или движок; стандартный Python и общие служебные функции уже созданного нового клиента. Токен/полный webhook URL не копируются в проект. Пользователь подтвердил системный доступ к существующему ключу.

## Исполнитель и смысл данных

Основной исполнитель — **директор**, навык `agency-director`. Он читает заявки/лиды, сделки, источники и UTM, историю стадий, счета и оплаты. Маркетолог и семантик получают нужные выводы; не нужно давать каждому агенту сырую базу клиентов. Новая роль аналитика не создаётся.

**Правило владельца от 12.11.2026: фактическую оплату фиксируют переводом счёта в «Оплачен».** Для текущего портала это новый счёт `entityTypeId=31`, стадия `DT31_2:P`; соответствие названия и семантики S подтверждено свежим `crm.status.list`. Правило записано в `payment_evidence` конфигурации. Для операционной аналитики директора это основание оплаты, а не гипотеза по названию поля. Банковскую сверку этим подключением не выполняли.

| Данные | Источник/поле | Как использовать |
|---|---|---|
| Лид/заявка | crm.lead.list/get | Дата создания, статус, источник, UTM, нужные пользовательские поля; запись CRM сама по себе ещё не квалифицированное обращение |
| Сделка | crm.deal.list/get | LEAD_ID, CATEGORY_ID, STAGE_ID, OPPORTUNITY, CURRENCY_ID; успех сделки и её сумма не заменяют оплату |
| Оплаченный счёт | crm.item.list, entityTypeId31, stageId DT31_2:P | Сумма opportunity, валюта currencyId, связь со сделкой parentId2; дедупликация по id счёта |
| Дата фиксации оплаты в CRM | crm.stagehistory.list, entityTypeId31 | CREATED_TIME перехода в оплачено; учитывать повторные записи/возвраты стадии. Это дата записи в CRM, не автоматически банковская дата |
| Отдельный платёжный документ | crm.item.payment.list/get | Доступный дополнительный источник; в проверенной выборке платежей сделок/счетов массивы пустые. Это не отменяет правило владельца |

Не складывать счёт и его отдельные платежи как независимую выручку. Повторный переход одного счёта в «Оплачен» не означает ещё одну оплату. В проверке пяти счетов получено семь строк истории — считать по ID счёта, историю разбирать отдельно. Валюты не суммировать между собой. Аннулирование/изменение стадии не доказывает сумму возврата денег. Срок оплаты `closedate` и время произвольного изменения `updatedTime` не использовать вместо даты оплаты.

Для связи с рекламой использовать наблюдаемые LEAD_ID, source/UTM и поля источника. Проверять TEST/дубли/потребность по доступным данным и условиям задачи. Не объявлять все записи портала заявками из Директа. Пользовательские поля «Прибыль» и «Себестоимость» найдены, но их формула и заполненность не подтверждены; их названия не доказывают рассчитанную маржу. Не импортировать старый журнал outcomes и его ошибки как состояние новой CRM.

## Возможности и запуск

[Каталог](bitrix24-api-catalog.md), `config/bitrix24-methods.json`: 81 релевантная операция CRM/оплат/обнаружения. Это не весь Битрикс24. Параметры передаются без фиксированного списка полей, 31-дневного периода, предела 20 страниц или 1 МБ на ответ. Дополнительный документированный метод добавляется в каталог с проверенным эффектом; имя метода не позволяет автоматически считать его чтением. `methods` — диагностический список, не единственная проверка доступности: некоторые универсальные CRM-методы отсутствовали в нём, но успешно ответили при вызове.

```bash
python3 scripts/bitrix24.py catalog
python3 scripts/bitrix24.py call --method scope
python3 scripts/bitrix24.py prepare --method crm.deal.list --params /absolute/path/query.json
python3 scripts/bitrix24.py call --method crm.deal.list --params /absolute/path/query.json
python3 scripts/bitrix24.py list-all --method crm.lead.list --params /absolute/path/query.json
python3 scripts/bitrix24.py list-all --method crm.item.list --items-key items --params /absolute/path/invoices.json
python3 scripts/bitrix24.py batch-many --params /absolute/path/commands.json
```

Для оплаченных счетов `invoices.json`:

```json
{"entityTypeId":31,"filter":{"stageId":"DT31_2:P"},"order":{"id":"ASC"},"select":["id","parentId2","stageId","opportunity","currencyId","createdTime"]}
```

Это выборка текущего состояния оплаченных счетов, не отчёт об оплатах за период. Для периода отдельно получить историю стадий с нужными границами, связать ID счетов и проверить повторные переходы. Для просмотра происхождения обращения получить связанную сделку и лид.

`commands.json` — объект вида `{"one":{"method":"crm.deal.get","params":{"id":123}}}`. `batch-many` отправляет любое число команд чтения штатными пакетами до 50 — предел Битрикс24, не общий предел задачи. Проверяет ошибки и наличие каждого alias. Поддерживает `$result[alias][field]` на предыдущую команду; между пакетами подставляет уже полученный результат, при отсутствующем результате сохраняет остаток без слепого исполнения. Нативный `call --method batch` тоже классифицирует каждую вложенную команду.

`list-all` следует `next/start` до конца без собственного предела страниц; для вложенного массива нужен `--items-key` (items у crm.item.list/stagehistory). Останавливается на ошибке/повторном курсоре с PARTIAL и уже полученными страницами. `start=-1` не выдаётся за полную выборку. Список из одного `call` или команды batch не является автоматически полным. При меняющейся CRM учитывать время снимка и сверять IDs/total; это не транзакционная банковская выгрузка. Для очень больших задач можно читать страницы отдельными `call` и сохранять частями, без накопления всей базы в памяти.

Полные ответы и параметры сохраняются в `~/.local/share/1pi-directologist4/` вне Яндекс.Диска, файлы0600. В stdout — статус, метаданные и путь. Не сохранять сырую CRM/телефоны/email/платёжные ссылки в синхронизируемом проекте и не печатать полный webhook. Журнал `bitrix24-requests.jsonl` содержит хеши запросов и результаты, без секрета. Нет автоматических повторов; при 429 учитывать ответ провайдера. Сроки/квоты провайдера не заменять собственными жёсткими числами.

## Проверенное и оставшееся

[Свидетельства](../work/bitrix24-connection/verification.json) сохраняют успешные методы, отказ и точный объём проб. Чтение лидов проверено на всех 157 доступных записях выбранного фильтра за четыре страницы; это не число коммерческих заявок. Для сделок проверены список и детали; API сообщил 1386 доступных сделок, выгружать их все для подключения не требовалось. Для новых счетов API сообщил 1063 записи, 610 находятся в подтверждённой оплаченной стадии; прочитаны первые50 оплаченных счетов, у всех есть связь со сделкой. Эти числа — снимок доступа на12.11, не отчёт по рекламе, не гарантированное число уникальных оплат за период.

У webhook scopes `crm`, `user_brief`. Расширенный `sale.payment.getFields` вернул `insufficient_scope`; права не расширялись. Доступные методы CRM и правило оплаченного счёта позволяют вести текущую задачу без этого scope. Отдельно банковская выписка, возвраты и корректность ручного ведения всей базы не проверены. REST v3 использует иной протокол и этим клиентом не подключён; текущие нужные CRM-методы работают через REST RPC v2.

В конфигурации `writes_enabled=false`: текущий прямой запрет владельца на изменения CRM. Локальная подготовка изменяющих методов возможна; отправка блокируется до Keychain/сети, в том числе внутри batch. Сам webhook может иметь более широкие права — его scope не доказывает read-only. Не включать запись по наличию ключа или прав; текущая задача её не поручает. Реклама также не менялась.
