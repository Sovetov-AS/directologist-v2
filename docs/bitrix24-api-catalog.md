# Битрикс24: каталог для заявок, сделок и оплат

Проверено 12 ноября 2026 по официальным страницам REST и [репозиторию документации Bitrix24](https://github.com/bitrix24/b24restdocs). [JSON-каталог](../config/bitrix24-methods.json) содержит **81 операцию: 63 чтения, 17 изменяющих и контейнер batch**. У каждой обычной операции есть точное имя REST, HTTP POST, эффект, группа, источник и хеш прочитанного текста. Это релевантный задаче каталог, не весь Битрикс24 и не перечень доказанно доступных методов конкретного портала. При составлении каталога ключи и CRM не читались.

## Что входит

| Группа | Возможности |
|---|---|
| Обнаружение | methods, method.get, scope, server.time, app.info, profile |
| Заявки и сделки | lead/deal list/get/fields, пользовательские поля, товары, контактные связи, история стадий |
| Универсальные объекты | item list/get/fields, типы смарт-процессов, новые счета, категории |
| Воронки и источники | category, status, owner types, currency; старые dealcategory только как совместимость |
| Контекст обращения | чтение контактов/компаний и дел CRM; запрашивать только нужные данные |
| Оплаты | crm.item.payment и sale.payment, позиции оплаты, привязки заказов и CRM |
| Счета | современные счета через item entityTypeId=31; legacy crm.invoice отдельно отмечен |
| Изменения | Основные add/update/delete и payment.pay/unpay включены как write для правильной классификации; сейчас не выполнять |

Параметры select/filter/order/start, собственные поля и периоды не урезаются каталогом. Дополнительный метод подключается по текущей официальной документации с явной классификацией эффекта; отсутствие имени здесь не доказывает отсутствия возможности Битрикс24. REST v3 имеет отдельный протокол/маршруты и не должен автоматически отправляться через обычный REST v2. Текущее подключение не объявляется полным покрытием REST v3 или интерфейса.

## С чего проверить чтение

1. `scope` и `methods` — фактически предоставленные возможности текущего подключения; затем `method.get` при необходимости. Доступ пользователя к объектам и доступность REST на тарифе проверяются ответами портала, а не каталогом.
2. `crm.lead.fields`, `crm.deal.fields`, `crm.item.fields` — реальные доступные поля. Для первых списков достаточно ID, дат, стадий, источников, сумм и валют; не выгружать все телефоны/комментарии ради проверки.
3. `crm.lead.list` и `crm.deal.list` с `order={ID:DESC}` и нужным select. Полученный список — первая страница, не вся история. TEST/дубли и связь обращения со сделкой определяются по данным, а не по названию источника.
4. `crm.category.list` с `entityTypeId:2`, `crm.status.list`, `crm.stagehistory.list` — воронка, семантика статусов и доступная история. Текущее WON не доказывает, когда именно была достигнута стадия.
5. `crm.item.payment.list` с `entityTypeId:2, entityId:<реальный ID сделки>` — оплаты конкретной сделки. Для нового счета использовать тип31 и реальный ID счета. Не создавать оплату ради проверки.
6. При наличии scope sale и требуемых прав: `sale.payment.getFields`, затем `sale.payment.list` с нужными select/filter. Связи заказов с CRM — `crm.orderentity.list`; их поля — `crm.orderentity.getFields`.

## Как подтверждать оплату

`OPPORTUNITY`/`opportunity` — сумма сделки; WON — успешная стадия. Выставленный счет тоже не равен оплате. Дата создания сделки/счета не является датой поступления денег. [Пример Bitrix24 о дате оплаты](https://apidocs.bitrix24.ru/tutorials/crm/how-to-edit-crm-objects/how-to-set-paid-date-to-deal.html).

[crm.item.payment.list](https://apidocs.bitrix24.ru/api-reference/crm/universal/payment/crm-item-payment-list.html) возвращает оплаты одной сделки или нового счета: id, paid, datePaid, sum, currency и платежную систему. Типы объектов с оплатами —2 и31; для других типов пустой массив не означает отсутствие продаж. По актуальной русской странице все оплаты объекта возвращаются сразу, **start не поддерживается**. Англоязычные сгенерированные SDK-примеры про50/page противоречат этому описанию; не копировать их без проверки.

Платеж с `paid=Y` является отметкой об оплате **в CRM**, а не независимой банковской сверкой. Поля статуса могут меняться методами pay/unpay. При нескольких платежах учитывай каждый уникальный payment.id один раз; одна оплата может быть найдена через разные связанные объекты. Не складывай сумму сделки, счета и платежа как три поступления. Разделяй валюты и периоды по datePaid. Частичная оплата определяется суммой подтверждённых отдельных оплат относительно релевантного обязательства, а не числом успешных сделок.

[sale.payment.list](https://apidocs.bitrix24.ru/api-reference/sale/payment/sale-payment-list.html) с scope sale требует администратора по документации и даёт расширенные поля. Для возвратов/проверки основания полезны isReturn, payReturnNum, payReturnDate, psStatus, psSum, psCurrency, psInvoiceId, payVoucherNum, payVoucherDate. Точный состав уточнять через [sale.payment.getFields](https://apidocs.bitrix24.ru/api-reference/sale/payment/sale-payment-get-fields.html). Один isReturn без установленной суммы и смысла возврата не позволяет вычислить чистое поступление; неполные/противоречивые основания сохранять как неизвестное. Данные платежной системы/1С и банковская выписка — отдельные источники подтверждения, наличие реквизита не доказывает выполненную сверку.

## Атрибуция и качество заявок

Лид, обращение, контакт, сделка и оплата — разные сущности. Совпадение SOURCE_ID с условным кодом рекламы не доказывает путь конкретного клика. Читай SOURCE_ID/SOURCE_DESCRIPTION, UTM-поля и пользовательские идентификаторы, если они действительно есть в fields; не придумывай связь по yclid/clientID. Сохраняй существующие ID связей и дату наблюдения. Успешная сделка без оплаты и оплата старой сделки вне периода привлечения должны оставаться различимыми. Выводы о целевом обращении требуют содержания и коммерческого исхода; техническая TEST-форма не становится продажей.

## Пакеты, страницы и ошибки

[batch](https://apidocs.bitrix24.ru/settings/how-to-call-rest-api/batch.html) — контейнер до50 команд по пределу провайдера, не предел объёма задачи. Его эффект определяется **каждой вложенной командой**; POST или внешнее имя batch не делают пакет безопасным чтением. В режиме чтения все cmd должны быть известными read; вложенный batch не использовать. Сохраняй result и result_error по именам команд, а также доступные result_next/result_total; HTTP200 не означает успех всех элементов.

У многих списков REST v2 страница50 записей; продолжение задаётся start/next согласно методу. Не вводить общий предел50 объектов и не называть одну страницу полной выгрузкой. Платежный список CRM — отдельное исключение без пагинации. Для больших задач допустимы штатные пакетные запросы и дальнейшие страницы, без собственных дневных/месячных квот старого движка. [Общие ограничения провайдера](https://apidocs.bitrix24.ru/settings/performance/limits.html) зависят от продукта/тарифа и нагрузки; HTTP429 и ошибки прав нельзя обходить догадкой.

Ошибку RPC определяй по **наличию ключа error**, включая error=0/пустую строку с error_description. Нельзя считать пустой результат нулевым числом заявок, если запрос завершился ошибкой, отбором другой воронки или неполной пагинацией. Секрет webhook входит в URL: не писать полный адрес в журнал, исключения, preview и документы. OAuth refresh меняет токены и не является обычным чтением CRM; подключение к существующему webhook не требует переноса старого моста или его правил.

## Границы этой проверки

Каталог подтверждает публикацию выбранных операций и их назначение. Он не подтверждает текущие права портала, полноту исторических данных, наличие всех платежей/возвратов, автоматическую атрибуцию или банковскую сверку. Legacy invoice/category сохранены для явной проверки совместимости, не объявлены доступными без ответа портала. Реальные результаты подключения фиксирует директор отдельно. Настройки CRM, сделки, оплаты и рекламу при составлении каталога не изменяли.
